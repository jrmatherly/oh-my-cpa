## Red flags

- **Migration 069 runs on the first start after upgrade, in one transaction.** It adds a column (no rewrite), then scans every request record once to store `client_prefix` on rows whose client is known, then groups every record at or below the facts checkpoint into the two new tables. Timed on a file database on an Apple Silicon Mac with a throwaway test, rows spread so that almost every record is its own 15-minute bucket (the worst case for the rollup): 20,000 records 0.4 s, 200,000 records 3.2 s, 1,000,000 records 16.6 s. The file grew about 40% in that worst case (482 MB to 684 MB at 1M). A failure rolls the transaction back and the console does not start. The schema version becomes 69, so a backup taken afterwards is refused by a build that ships only through 068.
- **Earlier Hermes requests keep their old client.** Migration 069 keeps any stored client it can read, and the backfill skips `unknown` rows. Before commit 2 the classifier stored `HermesAgent/<ver>` as `hermesagent` and `codex_cli_rs/0.0.0 (Hermes Agent)` as `codex-cli` (two reviewers ran the pre-merge classifier). Insights and the request list show those beside Hermes Agent until the records age out. Left as upstream wrote it; a remap needs a decision on fork migrations.
- **New tables are upstream's, in upstream's files.** `lifecycle.go` and `readonly_query.go` list them. `client_prefix` is readable by the operator's read-only SQL; it is the minimised User-Agent prefix (`claude-cli/2.`), and `sanitizeClientPrefix` rejects one that carries a redaction marker.
- **The request export schema changed** from `omc.requests.v1` to `omc.requests.v2`. A script that checks the schema string needs the new value.
- Not checked: the console in a browser beyond the smoke run (the client column and the reset credit list were not looked at by eye), and the stale-chunk reload against a real upgrade.
